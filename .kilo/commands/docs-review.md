# Documentation Review and Improvement

## 1. Determine intent
Distinguish review-only from requested editing. Identify audience, purpose, canonical source, format, and expected level of detail. Do not edit when the user asked only for review.

## 2. Verify facts
- Read the actual source/configuration/API before documenting implementation behavior.
- Check official platform and tool documentation for syntax and version-specific claims.
- Mark proposals, assumptions, and unverified behavior explicitly.
- Check paths, command names, workflow names, Skill names, Agent IDs, and tool schemas against actual files/configuration.
- Never document a planned feature as implemented.

## 3. Improve the document
- Organize from purpose and prerequisites to steps, examples, verification, troubleshooting, and limitations.
- Prefer concise actionable instructions over repeated prose.
- Keep one canonical explanation; link to specialist references rather than duplicating them.
- Include copyable commands only when their syntax and side effects are understood.
- Protect secrets and private operational data.
- Preserve user terminology and approved decisions.

## 4. Acceptance
Check factual accuracy, completeness for the intended audience, internal consistency, working links/paths, executable examples, version notes, and absence of contradictory or stale instructions.

## 5. Report
State what was reviewed/changed, sources used, facts that remain unverified, and acceptance results. If no edit was requested, keep the task read-only.
